# 故障与恢复

| 现象 | 检查与处理 |
| --- | --- |
| 找不到 codex.exe / 不支持 queue | 运行 `codex queue --help`；用初始化参数明确指定当前产品附带的原生执行文件。不要换成隐藏模型或另一聊天。 |
| inbox 一直有任务 | 确认 WorkBuddy 已在对应目录的原生会话读取提示词并运行守候。普通终端里的 watcher 不能唤醒一个未接入的 WorkBuddy 会话。 |
| processing 长时间不变 | 查看原 WorkBuddy 会话和已产生文件。可能仍在工作，也可能已中断。不要自动搬回 inbox 或换 ID 再发。 |
| 只有 ids 记录，无任务 | 可能在编号预留后中断。先核对所有目录和原会话，保留记录；明确知道副作用与执行状态后再决定下一步。 |
| 已在 done/failed，无 results | 可能在归档与结果发布之间中断。根据真实执行证据补齐回报，不能重做任务来填记录。 |
| 结果有了但没有验收 | 运行 manager Status，看 logs 中 started、queued、queue_failed。queued 只表示消息入队，还需检查目标聊天是否可用、是否收到以及 reviews 是否生成。 |
| queue_failed 或投递状态不确定 | 同内容不会静默再投递。先看绑定聊天和原日志，再在目标聊天手动要求检查已有结果。不要直接删除状态文件尝试“修好”。 |
| PID 存在但 healthy=false | manager 同时核对脚本、队列和聊天身份。不要只凭 PID 或旧心跳判断健康；根据 message 修正绑定或正常停止旧实例。 |
| 同一任务重复提醒 | 检查是否有两个队列、不同聊天绑定、源文件变化或删除过状态。多个事件本身不应重复投递相同内容。 |
| 拒绝目录联接/越界路径 | 将工作区和队列放在常规本地目录。不要绕过检查、提高全局权限或改用凭证目录。 |
| 脚本被 Windows 策略阻止 | 遵守组织与本机的脚本策略；核对下载来源，按自己的正常审批流程运行。项目不会修改系统执行策略。 |
| 正常退出或重启后不领取 | 分别恢复 WorkBuddy 会话守候和结果监听。v0.1.0 没有登录自启动与系统重启恢复保证。 |

先运行 `scripts/doctor.ps1`。提交问题时只附去除隐私的版本、错误、复现步骤和最小样例。不要上传 bridge.local.json、真实任务、聊天编号或登录文件。
